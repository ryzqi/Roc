## 1. 项目定位

Roc 是一个 Windows 本地个人超级助手。它不是单纯聊天客户端，而是面向开发、研究写作、文件整理、知识管理、周期任务和个人工作流的桌面工作台。

第一版必须同时满足：

- Windows 桌面体验完整。
- 界面纯白极简、扁平化、圆润。
- 动画顺滑但不拖慢响应。
- 常驻与空闲内存受控。
- 文件、Git、终端、MCP、Skills、记忆和任务轨迹是一等能力。
- 底层 agent 编排使用 Deep Agents TypeScript 库。

本文是当前技术栈与布局事实源。`想法.md` 负责产品功能边界，`记忆系统.md` 负责记忆系统原则。本文只记录已经逐项确认的技术和布局结论，未讨论或未确认的点不写入。

```text

│   ├── AgentService
│   │   └── Deep Agents TypeScript createDeepAgent(...)
│   ├── MemoryService
│   ├── PermissionService
│   ├── AuditService
│   ├── ProviderService
│   ├── McpService
│   ├── SkillService
│   ├── WebReadService

    ├── %USERPROFILE%\.roc\memory\
    ├── %USERPROFILE%\.roc\logs\
    └── %USERPROFILE%\.roc\diagnostics\
```

### 3.1 Electron 主路径

Electron 继续作为第一版桌面主路径。

采用原因：

- 与最初版一致。
- 与 Deep Agents TypeScript、Node 主进程、MCP、Skills、`node-pty` 和本地工具生态整合成本最低。
- Windows 托盘、全局快捷键、窗口管理、菜单、文件对话框和打包路径成熟。

窗口壳层约束：

- 首屏不得显示系统标题栏或系统菜单栏。
- 主窗口使用自绘薄工作带承载品牌、少量状态、设置入口和窗口控制。
- 拖拽、最小化、最大化/还原、关闭继续由主进程受控提供。

约束：

- 渲染进程不得直接获得 Node 能力。
- 使用 `contextIsolation` 和 preload IPC。
- 主进程负责能力编排，但不得被长任务或重计算阻塞。
- 长任务、索引、embedding、MCP 长连接和终端输出必须做限流、分页或后台队列。

### 3.2 AgentService 与 Deep Agents TypeScript

底层 agent 编排使用 Deep Agents TypeScript 库，核心入口是 `createDeepAgent(...)`。

`AgentService` 负责：

- 创建和维护 Deep Agents 实例。
- 注入模型、tools、skills、subagents、memory、backend、store、checkpointer 和 `interruptOn` 配置。
- 将普通聊天升级为任务会话。
- 管理任务线程、执行轮次、追加指令和恢复。
- 接收 Deep Agents 工具调用、子任务结果、审批中断和最终输出。
- 把模型调用、工具调用、MCP 调用、终端操作和记忆引用写入任务轨迹。

Deep Agents 原生能力映射：

| Deep Agents 能力 | Roc 中的用途                     |
| -------------- | ---------------------------- |
| `tools`        | MCP 工具、本地文件/Git/终端/网页工具、记忆工具 |
| `skills`       | 本地可复用工作方法和流程说明               |
| `subagents`    | 专业子任务，例如代码审查、资料整理、检索、验证      |
| `write_todos`  | 任务计划和执行步骤                    |
| `task`         | 子任务委派                        |
| `memory`       | 启动时必须加载的紧凑规则和上下文             |
| `backend`      | Deep Agents 虚拟文件系统和上下文管理     |
| `store`        | 跨线程或跨会话的持久状态                 |
| `checkpointer` | 中断、恢复和长任务延续                  |
| `interruptOn`  | 高风险工具调用审批                    |

约束：

- Deep Agents 不直接写 Roc 长期记忆文件和 SQLite 表。
- 长期记忆通过 `MemoryService` 暴露的受控工具访问。
- 需要审批的工具必须通过 `interruptOn` 或 Roc 的 `PermissionService` 进入确认流。
- 默认使用主进程内 `AgentService`，但长任务执行必须异步化，避免阻塞主进程事件循环。

### 3.3 生态复用优先级

Roc 的 agent 层按以下顺序复用 LangChain 生态能力：

1. Deep Agents 负责长任务 agent harness：planning、虚拟文件、subagents、skills、memory middleware、HITL 和 streaming。
2. LangGraph 负责 Deep Agents 底层 thread、checkpointer、store、resume、状态历史和需要显式图控制的子流程。
3. LangChain 负责模型抽象、tool schema、structured output、middleware、MCP adapter、RAG loader/splitter/retriever 等基础能力。
4. Roc 自己只实现桌面产品边界：Electron UI、IPC、权限、审计、恢复点、任务轨迹、`.roc` 数据目录、Markdown 记忆真相源、SQLite 元数据和 Windows 打包。

直接复用优先于自研包装。只有当官方能力不能满足 Roc 的权限、审计、恢复点、UI 追踪或本地数据边界时，才允许在 Roc 服务层外包一层适配器。

当前版本锚点：

| 包 | 当前核验版本 | Roc 用途 |
| --- | --- | --- |
| `deepagents` | `1.10.0` | `createDeepAgent`、内建 middleware、backend、skills、subagents、streaming |
| `langchain` | `1.4.0` | model/tool 抽象、structured output、middleware、RAG 组件 |
| `@langchain/langgraph` | `1.3.0` | checkpointer、store、thread resume、状态历史、图执行 |
| `@langchain/mcp-adapters` | `1.1.3` | MCP server 工具发现和 LangChain tool 转换 |

版本写入开发依赖前必须重新查 registry；本文版本只作为 2026-04-28 的决策快照。

### 4.7 RTK 原生集成设计

RTK 在 Roc 中的定位不是外部开发者工具，也不是要求用户单独安装的 CLI。第一版中，RTK 作为 Roc 安装包自带的内置命令压缩引擎，由 Roc 主进程受控拉起和调度。

集成目标：

- 用户安装 Roc 后即可直接使用 RTK 相关能力。
- RTK 只作为 Roc 的内部执行组件出现，不要求用户配置 PATH。
- RTK 的输出压缩能力服务于 agent 发起的命令执行和任务轨迹，不改变 Roc 的主控制面。
- RTK 相关配置、统计、tee 原始输出和诊断信息统一纳入 `~/.roc` 边界。

#### 4.7.1 角色与边界

RTK 在 Roc 中只负责一件事：压缩命令输出，减少 agent 在任务执行链中消耗的无效上下文。

它不负责：

- 取代 Roc 的任务编排。
- 取代 Roc 的权限、审批、审计和恢复点。
- 取代用户可见的嵌入式终端。
- 取代 MCP、Skills、记忆或 Provider 管理。

因此，RTK 的正确位置是 `TerminalService`、`TaskService` 和 `AgentService` 之间的内部命令执行层，而不是独立 UI 功能，也不是单独的外部 agent hook 体系。

#### 4.7.2 接入形态

第一版采用“随安装包分发的内部二进制 + Roc 自定义适配层”方案。

建议形态：

- Roc 安装包内置 `roc-rtk.exe`。
- `roc-rtk.exe` 由主进程服务按绝对路径拉起。
- 不依赖用户环境变量中的 `rtk`。
- 不要求运行 `rtk init`、不依赖外部 `AGENTS.md` 注入、也不依赖外部 hook 配置。

采用原因：

- 上游 RTK 当前是 Rust CLI 代理，不是可直接嵌入的 TypeScript SDK。
- 上游 RTK 的自动改写主要面向外部 agent hook；Roc 自己已经有主进程执行链和任务轨迹，不应重复引入第二套控制面。
- Windows 原生环境下，上游 RTK 的完整 hook 体验并不成立；而 Roc 的第一版明确是 Windows 原生桌面应用。

#### 4.7.3 调用链设计

RTK 应由 Roc 自己决定何时使用，而不是让 RTK 自己在外部拦截命令。

推荐调用链：

```text
AgentService / TaskService
  -> PermissionService
  -> TerminalService / ShellExecutionService
  -> RtkService
  -> roc-rtk.exe 或原始命令
  -> AuditService
  -> Task 轨迹 / Doctor / Diagnostics
```

其中：

- `AgentService` 决定当前命令是否属于 agent 发起的非交互执行。
- `PermissionService` 先完成工作区边界、高风险动作和长期授权判断。
- `RtkService` 负责决定走 RTK 压缩还是走原始命令。
- `AuditService` 负责记录原始命令、压缩后输出、原始输出引用、执行时长、退出码和 bypass 原因。

#### 4.7.4 适用范围

第一版默认只让 RTK 作用于 agent 发起的非交互命令。

优先接入的命令类型：

- Git：`status`、`log`、`diff`、`show`。
- 搜索与读取：`rg`、`grep`、`find`、`cat`、`head`、`tail`。
- 构建与测试：`cargo test`、`cargo build`、`pnpm list`、`vitest`、`jest`、`pytest`、`playwright test`。
- 基础系统信息：`ls`、`tree`、`wc`、`env`。
- 容器与云工具：`docker`、`kubectl`、`aws`。

默认不接入的场景：

- 用户手动操作的嵌入式终端交互会话。
- 依赖原始格式的 TUI 程序。
- 长时间流式刷新的交互命令。
- 对输出顺序、ANSI、分页或精确原文高度敏感的命令。

#### 4.7.5 与嵌入式终端的关系

Roc 的右侧嵌入式终端是给用户直接查看和接管的工作区能力，不应默认被 RTK 压缩。

约束：

- 用户打开的终端面板默认展示原始输出。
- agent 后台执行的 shell/tool 命令可以走 RTK。
- 如果用户从任务轨迹进入“查看原始输出”，必须能看到未压缩版本。
- 如需在终端面板内复用 RTK，只能作为显式切换项，而不是默认行为。

#### 4.7.6 数据目录与配置边界

RTK 的所有运行数据必须纳入 Roc 已确认的 `~/.roc` 根目录，不能额外散落到独立的 `rtk` 目录。

建议目录：

```text
%USERPROFILE%\.roc\
├── config\
│   └── rtk.toml
├── tools\
│   └── roc-rtk.exe
├── rtk\
│   ├── history.db
│   ├── tee\
│   ├── filters\
│   └── audit\
├── logs\
└── diagnostics\
```

约束：

- 不使用上游默认的独立 `~/.config/rtk` 或 `%APPDATA%\\rtk` 作为长期事实源。
- RTK 配置、tee 原始输出、统计库和附加过滤器都由 Roc 统一托管。
- RTK 统计数据属于 Roc 诊断数据的一部分，需与任务轨迹和 Doctor 一致。

#### 4.7.7 RtkService 职责

`RtkService` 是 Roc 对 RTK 的唯一适配入口。

负责：

- 解析当前命令是否适合通过 RTK 执行。
- 选择 `roc-rtk.exe` 或原始命令路径。
- 注入 Roc 统一的 RTK 配置目录、统计库路径和 tee 目录。
- 记录 bypass 原因，例如交互命令、输出格式不兼容、命令未支持、用户显式要求原始输出。
- 返回结构化执行结果给 `TaskService` 和 `AuditService`。

不负责：

- 直接决定权限。
- 直接写入任务业务状态。
- 直接暴露给渲染进程执行。

#### 4.7.8 输出与审计契约

RTK 不得破坏 Roc 的可见性和可追溯性。

每次经 RTK 的执行至少记录：

- 原始命令。
- 规范化后的实际执行命令。
- 是否经过 RTK。
- RTK 二进制版本。
- 压缩后输出。
- 原始输出保存路径或引用。
- 退出码。
- 执行时长。
- 是否触发 tee。
- bypass 原因。

任务轨迹和 Doctor 至少要能展示：

- 本任务哪些命令走了 RTK。
- 哪些命令被跳过以及原因。
- RTK 是否可执行。
- RTK 原始输出恢复路径是否可读。
- 近一段时间的压缩收益摘要。

#### 4.7.9 安全与失败降级

RTK 在 Roc 中必须遵守“失败不阻断用户工作流”的原则，但不能吞掉 Roc 自己的权限控制和诊断信息。

规则：

- 如果 RTK 过滤失败，应降级为原始命令执行，并将原因写入任务轨迹。
- 如果 RTK 二进制缺失、损坏或版本不兼容，Roc 应在 Doctor 中报错，但任务执行仍可退回原始模式。
- RTK 的压缩输出只作为上下文优化结果，不得替代原始审计事实源。
- 来自网页、日志、外部文件等不可信输入的内容，即使被 RTK 压缩，也仍然是不可信上下文。

#### 4.7.10 打包与发布边界

第一版交付目标不是“告诉用户如何安装 RTK”，而是“Roc 安装后自带 RTK 能力”。

要求：

- Windows 安装产物内包含 `roc-rtk.exe`。
- 主进程启动时完成 RTK 可执行文件存在性检查。
- 如果 RTK 资源缺失，Doctor 给出“安装包不完整 / 资源损坏”的诊断。
- 打包后的路径解析必须稳定，不能依赖开发态目录结构。

#### 4.7.11 推荐实现策略

第一版建议以“Roc 维护的薄适配 fork”接入 RTK，而不是完全原样使用上游。

最小必要改动：

- 统一 RTK 的配置根目录到 `~/.roc`。
- 统一 tracking DB、tee 目录、过滤器目录和审计目录。
- 默认关闭 telemetry。
- 将二进制名称改为 `roc-rtk.exe`，避免与用户系统里已有 `rtk` 冲突。

不建议第一版做的事：

- 不做外部 hook 安装向导。
- 不做面向用户的 RTK 独立设置中心。
- 不做让用户手动维护 RTK 版本。
- 不做让用户单独安装或升级 RTK。

### 4.8 网络搜索与网页读取原生集成设计

Roc 第一版需要把“找资料”和“读网页”拆成两条能力链，而不是让多个外部服务同时承担搜索和读取。

正式结论：

- `web_search` 默认走 Exa 官方 Hosted MCP：`https://mcp.exa.ai/mcp`。
- `web_read` 默认走 Jina Reader：`https://r.jina.ai/<url>`。
- Exa 负责找候选来源和返回结构化搜索结果。
- Reader 负责读取已知 URL 并转成适合 agent 消费的正文。

#### 4.8.1 角色与边界

Exa MCP 和 Jina Reader 在 Roc 中的职责必须固定：

- Exa MCP 只作为默认网络搜索能力。
- Jina Reader 只作为默认网页读取能力。
- 搜索返回的是候选来源、摘要和继续阅读入口。
- 读取返回的是单个已知 URL 的正文、标题、来源和读取元数据。

它们不负责：

- 取代 Roc 的任务编排、审批、审计和恢复点。
- 直接写入 Roc 的长期记忆。
- 绕过聊天输入框中的 MCP 启用选择和长期授权策略。
- 把网页内容当作可信系统指令。

#### 4.8.2 Exa MCP 接入形态

第一版采用“内置官方远程 MCP 预设”方案接入 Exa，而不是在 Roc 内再写一套 Exa HTTP 客户端。

接入要求：

- Roc 安装后内置一个 Exa 官方 MCP 预设。
- 预设地址固定为 `https://mcp.exa.ai/mcp`。
- 预设由 `McpService` 管理，与普通 MCP 服务共用状态、授权、测试和审计链路。
- 默认启用的工具收敛为 `web_search_exa`。
- 第一版允许按需启用 `web_search_advanced_exa`。
- 第一版默认不把 `web_fetch_exa` 作为主读取链路暴露，避免与 `web_read` 双轨重叠。

采用原因：

- Exa 官方 Hosted MCP 已经符合 Roc 的 MCP 管理模型。
- 远程 MCP 形态更适合纳入现有能力管理、授权和 Doctor。
- 把搜索维持在 MCP 层，能避免 Roc 自己重复维护搜索 provider 路由。

#### 4.8.3 Jina Reader 接入形态

第一版采用“主进程原生 HTTP 封装 + 内置 `web_read` tool”方案接入 Jina Reader，而不是把 Reader 项目本身嵌入 Electron 运行时，也不是再包一层 MCP。

接入要求：

- `WebReadService` 作为 Roc 主进程内的一等服务存在。
- `WebReadService` 负责调用 `r.jina.ai` 读取已知 URL。
- `web_read` 通过 Roc 自己的工具层暴露给 Deep Agents，而不是通过 MCP 转发。
- 第一版只暴露最小必要参数：`url`、`responseMode`、`timeoutSeconds`、`noCache`。
- `responseMode` 第一版只支持 `markdown` 和 `text` 两种稳定输出。

采用原因：

- Roc 已经有自己的工具层、审计链和权限链，没有必要把单一网页读取能力再绕到 MCP。
- Reader 的正确位置是 Roc 的内置网页读取底座，不是独立插件市场能力。
- Roc 需要自己决定何时读取网页、如何标记不可信上下文，以及如何进入任务轨迹。

#### 4.8.4 搜索与读取的统一调用链

推荐调用链：

```text
AgentService / TaskService
  -> PermissionService
  -> web_search: McpService -> Exa Hosted MCP
  -> web_read: WebReadService -> Jina Reader
  -> AuditService
  -> Task 轨迹 / Doctor / Diagnostics
```

路由规则：

- 用户或 agent 需要“找资料”时，优先走 `web_search`。
- 用户或 agent 已有明确 URL 时，优先走 `web_read`。
- 深度研究时先走 `web_search`，再对选中的 URL 走 `web_read`。
- 第一版不把 `https://s.jina.ai` 作为默认搜索主链。

#### 4.8.5 工具契约、数据边界与不可信上下文

`web_search` 和 `web_read` 都必须纳入 Roc 的统一工具契约。

至少记录：

- 调用来源。
- provider 或服务来源。
- 查询词或 URL。
- 最终来源 URL。
- 调用时间。
- 结果摘要。
- 失败原因。
- 是否命中缓存或远程复用缓存。

约束：

- 搜索结果和网页正文都属于不可信上下文。
- 搜索结果和网页正文只能作为参考资料，不能直接变成系统指令。
- 未经用户确认或后续整理流程，网页内容不得直接晋升为长期记忆。
- 连接配置、授权记录、最近错误和诊断结果统一纳入 `~/.roc` 边界。
- 不把 Exa 或 Reader 的凭据、请求头或敏感参数写入日志、诊断包或任务正文。

#### 4.8.6 设置页、Doctor 与审计要求

设置页和 Doctor 必须能解释这两条能力链的当前状态。

设置页至少展示：

- Exa 官方 MCP 预设是否已启用。
- Exa 搜索凭据状态与最近错误。
- Reader 读取连接状态与最近错误。
- 网页读取允许访问范围。
- 网页读取与网络搜索的连接测试入口。

Doctor 至少检查：

- Exa MCP 握手是否成功。
- Exa 工具发现是否完整。
- Exa 凭据或鉴权是否可用。
- Reader 读取链路是否可访问。
- Reader 读取失败时是否能返回明确错误分类。

任务轨迹至少展示：

- 本轮是否启用了 Exa MCP。
- 哪些搜索调用走了 Exa。
- 哪些网页读取调用走了 Reader。
- 失败、重试、降级和放弃原因。

#### 4.8.7 第一版不做的事

- 不把 Jina Reader 源码仓直接嵌进 Roc 进程内运行。
- 不额外实现一套与 Exa MCP 并行的 Exa HTTP 客户端。
- 不让 Exa `web_fetch_exa` 和 Reader `web_read` 同时成为默认读取主链。
- 不让 `s.jina.ai` 和 Exa MCP 同时成为默认搜索主链。
- 不把网页搜索或网页读取扩展成外部平台消息入口。

## 6. Deep Agents 原生能力与 Roc 能力映射

### 6.0 直接复用 / Roc 自研边界

| 能力 | 默认实现 | Roc 是否自研 |
| --- | --- | --- |
| 多步计划 | Deep Agents `write_todos` / `TodoListMiddleware` | 不自研计划引擎，只做任务轨迹映射 |
| Agent 虚拟文件 | Deep Agents filesystem backend / middleware | 不直接暴露宿主文件；Roc 做受控 backend 路由 |
| 同步子任务 | Deep Agents `task` / `SubAgentMiddleware` | 不自研子代理协议，只做类型、权限和事件映射 |
| 异步子任务 | Deep Agents async subagents + 本地 Agent Protocol runtime | Roc 只做本地 runtime 管理和 UI 状态 |
| Skills | Deep Agents `SkillsMiddleware` | Roc 做导入、校验、授权和路径管理 |
| 审批中断 | Deep Agents `interruptOn` / LangChain HITL middleware / LangGraph resume | Roc 做策略、审批 UI、审计和恢复点 |
| Streaming | Deep Agents / LangGraph streaming | Roc 只转换为任务事件和 UI 增量 |
| Checkpoint / resume | LangGraph checkpointer + stable `thread_id` | Roc 做 threadId、runId 和任务状态绑定 |
| 跨线程轻量状态 | LangGraph store / Deep Agents `StoreBackend` | 只存 agent 轻量状态，不替代长期记忆 |
| MCP 工具接入 | `@langchain/mcp-adapters` | Roc 做配置、授权、健康检查和审计 |
| 结构化输出 | LangChain structured output / schema | Roc 用于计划、诊断、记忆候选和工具结果校验 |
| RAG 基础件 | LangChain loaders / splitters / retrievers / vector store 接口 | Roc 只保留本地文件真相源、索引和预算策略 |

### 6.1 Tools

Roc 的 MCP、本地文件、Git、终端、网页搜索、网页读取、记忆访问都作为 Deep Agents tools 暴露。

工具要求：

- 名称清晰。
- schema 明确。
- 描述必须说明何时使用、访问范围和副作用。
- 调用结果进入任务轨迹。
- 高影响工具进入审批策略。
- 由 agent 发起的非交互 shell/tool 命令可经 `RtkService` 走 RTK 压缩，但该行为对用户必须可见、可回看原始输出、可诊断。

### 6.2 Skills

Roc 的 Skills 采用 Deep Agents 原生 skills。

Skills 用于承载：

- 代码审查流程。
- 资料整理流程。
- 周报/日报流程。
- 项目复盘流程。
- 文件归档流程。
- 开发任务推进流程。

约束：

- Skill 是工作方法，不是第三方插件市场。
- Skill 只在相关任务中按需加载。
- Skill 触发的工具调用仍必须进入任务轨迹和审批策略。

### 6.3 Subagents

Roc 使用 Deep Agents subagents 承接专业子任务。

可选子任务类型：

- 代码审查。
- 资料检索。
- 文件整理。
- 测试验证。
- 记忆整理。
- 诊断分析。

约束：

- 子任务结果必须回到主任务轨迹。
- 子任务不能绕过授权策略。
- 子任务不直接写长期记忆，必须通过 `MemoryService`。

### 6.4 LangChain / LangGraph 可直接使用能力

Roc 不需要自研以下底层能力：

- 不自研模型调用抽象；使用 LangChain model 接口承接 OpenAI-compatible、Anthropic-compatible、Ollama 和 Custom provider。
- 不自研 tool schema / tool call 基础协议；使用 LangChain tool 定义，Roc 只补风险、scope、审计元数据。
- 不自研 typed JSON 解析；需要结构化结果时使用 LangChain structured output，并用 Roc schema 做二次业务校验。
- 不自研通用 middleware 链；模型调用前后、工具调用前后、审批、脱敏、重试和策略注入优先用 LangChain middleware。
- 不自研 graph checkpoint；审批恢复、长任务恢复和状态历史使用 LangGraph checkpointer / store。
- 不自研 MCP client 协议适配；MCP server 连接和工具转换优先用 `@langchain/mcp-adapters`，Roc 保留配置、授权、Doctor 和审计。
- 不自研 RAG 基础流水线；加载、切分、embedding、检索、MMR 和 metadata filter 优先用 LangChain 组件，Roc 保留 Markdown 记忆真相源和 SQLite/FTS5/sqlite-vec 索引边界。

## 7. 记忆系统

### 7.1 记忆原则

记忆系统遵循 `记忆系统.md`：

- 记忆不是日志，是选择性压缩和策展。
- 策展记忆与原始会话回忆分离。
- 热记忆、暖记忆、冷记忆、会话回忆层分离。
- 普通对话潜在记忆先进入候选区。
- 记忆写入、修改、合并、禁用、恢复、删除、压缩整理、升降级、冲突裁决和自动遗忘都必须可审计。

### 7.2 MemoryService

`MemoryService` 是 Roc 长期记忆的唯一写入口。

负责：

- 热记忆加载。
- 暖记忆检索。
- 冷记忆检索。
- 会话回忆检索。
- 候选记忆。
- 冲突检测。
- 合并与升降级。
- FTS5 索引维护。
- sqlite-vec 缓存维护。
- 召回调试。
- 审计日志。

Deep Agents 只能通过受控工具访问：

- `memory_search`。
- `memory_get`。
- `memory_write`。
- `session_search`。
- `memory_status`。

### 7.3 存储路径

```text
%USERPROFILE%\.roc\
├── config\
├── roc.sqlite
├── memory\
│   ├── hot\
│   ├── warm\
│   ├── cold\

│   ├── staging\
│   └── skills\
├── indexes\
├── logs\
└── diagnostics\
```

工作区目录是任务执行边界，不是 Roc 全局配置或长期记忆默认保存位置。

## 8. 授权与审批

### 8.1 默认策略

Roc 第一版采用默认高自动化策略。

默认可直接执行：

- 只读查询。
- 工作区内低风险读取。
- 状态检查。
- 本地索引查询。
- 无副作用工具调用。

必须确认或中断：

- 工作区外写入、删除、移动或执行。
- 删除记忆。
- 覆盖已有有效记忆。
- Git push。
- 批量删除。
- 批量覆盖。
- 修改系统环境。
- 访问或写入外部服务。
- 暴露凭据或敏感信息的动作。

Deep Agents 使用 `interruptOn` 承接需要确认的工具。

Roc 的 `PermissionService` 负责：

- 将工具风险映射到 `interruptOn`。
- 展示待确认动作。
- 支持批准、拒绝和编辑参数。
- 将审批结果写入任务轨迹。
- 将长期授权写入可撤销授权记录。

### 8.3 审计

以下内容必须进入任务轨迹或审计日志：

- 能力启用来源。

- MCP 调用。
- Skill 触发。
- Subagent 委派。
- 终端命令。
- RTK 是否介入、介入版本、介入结果和 bypass 原因。
- 文件写入。
- Git 操作。
- 记忆写入和删除。
- 审批决定。
- 恢复点。

## 9. 性能与内存

### 9.1 预算

- 空闲内存占用 `< 300MB`，以常驻托盘状态为主要观察点。
- 对话流式响应需要在 500ms 内给出明确视觉反馈。
- 检索优先 FTS5，向量索引在后台构建。
- 首屏不得等待完整文件树、全部历史会话、全部记忆或全部终端日志加载。

### 9.2 控制手段

- 单主窗口优先。
- 四面板内容分区加载。
- 文件树虚拟滚动。
- 历史会话分页。
- 任务事件分页。
- 终端输出环形缓冲和日志落盘。
- RTK 过滤输出与原始输出分离存储，避免前端为长日志保留双份常驻内存。
- Monaco、PDF、Office 预览懒加载。
- embedding、索引重建、记忆整理进入后台队列。
- MCP 长连接空闲释放。
- Deep Agents 长任务异步执行，不阻塞主进程 UI 和 IPC。

### 9.3 性能验证

每个阶段都需要在 Windows 上验证：

- 冷启动时间。
- 主窗口打开时间。
- 空闲内存。
- 托盘常驻内存。
- 打开文件树后的内存。
- 打开终端后的内存。
- 长任务运行时内存。
- 终端大量输出时前端内存是否稳定。
- RTK 启用与未启用时的任务轨迹体积差异。
- RTK tee 原始输出写盘是否稳定。
- RTK 降级到原始命令时是否仍可完成任务。
- Exa 搜索请求的平均延迟、失败率和任务轨迹体积。
- Reader 读取大页面或动态页面时的延迟、失败率和结果大小。
- FTS5 查询耗时。
- 向量索引构建是否阻塞 UI。

## 11. RTK 详细实施清单

以下清单是第一版 RTK 原生集成的正式实施路径。

### 11.1 Wave A：上游收编与二进制准备

- 选择固定的 RTK 上游版本，记录来源与校验方式。
- 建立 Roc 自己的 RTK fork 或 vendor 仓来源。
- 将二进制名收敛为 `roc-rtk.exe`。
- 调整默认配置根目录，确保所有运行数据可指向 `~/.roc`。
- 默认关闭 telemetry，并确保 UI 中未显式开启前不产生外部上报。
- 建立 Windows 构建脚本，输出可被 Electron 打包直接消费的产物。

验收：

- 本地可生成 `roc-rtk.exe`。
- 在不依赖 PATH 的情况下可通过绝对路径执行。
- 不会写入独立的 `rtk` 默认目录。

### 11.2 Wave B：主进程服务层接入

- 新增 `RtkService`。
- 新增 `ShellExecutionService` 或在现有终端/命令执行服务中抽出统一执行入口。
- 设计 `shouldUseRtk(command, context)` 判断逻辑。
- 设计 bypass reason 枚举。
- 约定返回结果结构：`stdout`、`stderr`、`exitCode`、`usedRtk`、`teePath`、`bypassReason`、`durationMs`。

验收：

- agent 发起的命令可以通过统一入口执行。
- 同一入口既支持 RTK 模式，也支持原始模式。
- 所有错误都能回传结构化结果，而不是只打印日志。

### 11.3 Wave C：命令白名单与分流

- 建立第一版 RTK 白名单命令集。
- 建立交互命令黑名单。
- 区分三类执行场景：
- agent 后台非交互命令。
- 用户嵌入式终端交互会话。
- 系统内部诊断命令。
- 明确哪些命令允许手动强制 raw，哪些允许手动强制 rtk。

验收：

- 用户打开的终端面板默认看到原始输出。
- agent 后台命令按白名单走 RTK。
- 黑名单命令不会误走 RTK。

### 11.4 Wave D：任务轨迹与审计接入

- 在任务事件模型中新增 RTK 相关字段。
- 记录原始命令与实际执行命令。
- 记录压缩输出和原始输出路径。
- 记录 RTK 版本、tee 结果和 bypass 原因。
- 在任务详情页提供“查看原始输出”入口。

验收：

- 任务轨迹可区分 RTK 与非 RTK 命令。
- 每次 RTK 降级都能看到原因。
- 原始输出可被二次查看，而不需要重新执行命令。

### 11.5 Wave E：`.roc` 数据目录收口

- 在 `~/.roc` 下创建 RTK 专属子目录。
- 建立 `rtk.toml` 生成逻辑。
- 将 tracking DB、tee、filters、audit 全部指向 `~/.roc`。
- 明确清理策略、容量上限和日志轮转策略。

验收：

- 运行后不会在用户目录其他位置新增长期 RTK 数据。
- 删除 `~/.roc\\rtk` 不会破坏 Roc 其他核心数据结构。
- Doctor 能识别路径异常和权限异常。

### 11.6 Wave F：Doctor 与设置页接入

- Doctor 检查 `roc-rtk.exe` 是否存在、可执行、版本是否匹配。
- Doctor 检查 RTK 配置路径、tracking DB、tee 目录读写状态。
- Doctor 展示最近 bypass 统计和失败原因。
- 设置页增加 RTK 相关基础开关，但不暴露复杂外部 hook 配置。

设置项建议只包含：

- 是否对 agent 后台命令启用 RTK。
- 是否保留原始 tee 输出。
- 原始输出保留上限。
- 是否显示压缩收益摘要。

验收：

- Doctor 可以在缺失二进制、路径无权限、配置损坏时给出明确修复建议。
- 设置变更进入草稿态并保存后生效。

### 11.7 Wave G：打包与安装集成

- 将 `roc-rtk.exe` 纳入 Electron 打包清单。
- 处理开发态与生产态资源路径差异。
- 首次启动时验证 RTK 资源是否存在。
- 缺失时进入 Doctor，而不是静默失败。

验收：

- 打包后的 Windows 产物可直接使用 RTK。
- 用户无需额外安装或配置。
- 资源缺失时 Roc 可以自检并给出错误定位。

### 11.8 Wave H：验证与性能基线

- 对同一批命令比较 RTK 开启/关闭时的任务轨迹体积。
- 验证大输出命令的前端内存占用是否下降。
- 验证 tee 落盘后可成功查看原始输出。
- 验证 RTK 故障时自动回退到原始模式。
- 验证工作区外命令、高风险命令和审批流没有被 RTK 绕过。

验收：

- 有明确的 RTK 收益证据，而不是只停留在设计层。
- 无 fresh verification 不宣称“RTK 已集成完成”。

### 11.9 Wave I：后续扩展但不纳入第一版

- 更细粒度的命令策略中心。
- RTK 自定义过滤器管理 UI。
- 项目级 RTK 策略覆盖。
- 面向用户可见的长期压缩收益仪表盘。
- 终端面板内显式切换“原始/压缩查看”。
