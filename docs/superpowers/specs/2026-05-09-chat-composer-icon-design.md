# Chat Composer 图标语义重设计

## 1. 目标

将聊天输入框下方 4 个入口的图标重设计为更符合产品语义的现成图标，提升首次识别性：

- 上传文件
- 工具
- 技能
- 模型

本次工作只解决图标语义问题，不改变交互结构、状态逻辑或测试锚点。

## 2. 当前状态

当前入口位于 `src/renderer/App.tsx` 的 `ChatView` 底部工具栏区域，相关样式位于 `src/renderer/styles.css`。

当前语义问题如下：

- `上传文件` 使用 `tray-upload`，语义接近但偏托盘上传。
- `工具` 使用 `stack`，更像层叠列表，不像可调用工具。
- `技能` 使用 `checklist`，更像待办清单，不像能力包。
- `模型` 使用 `panel-capture`，与模型选择语义不匹配。

仓库当前已安装 `lucide-react@1.11.0`，可以直接复用现成图标，无需新增图标库。

## 3. 设计边界

### 3.1 在做范围

- 仅替换聊天输入框下方 4 个入口的图标。
- 优先使用仓库现有 `lucide-react` 图标。
- 保持现有 hover、active、badge、popover 行为不变。

### 3.2 不做范围

- 不修改按钮文案、按钮数量或按钮顺序。
- 不修改 `data-testid`、`aria-label`、popover 内容或交互方式。
- 不修改模型选择、工具选择、技能选择、附件选择的业务逻辑。
- 不扩展新的图标系统、主题状态或配置项。
- 不顺带重构 `PreviewIcon` 的其他分支。

## 4. 最终图标映射

采用“严格产品语义”方案，最终映射固定如下：

- `上传文件` -> `FileUp`
- `工具` -> `Wrench`
- `技能` -> `Sparkles`
- `模型` -> `Bot`

### 4.1 选择理由

- `FileUp` 直接表达“选择并附加文件”这一动作。
- `Wrench` 对“工具能力”有清晰、普适的认知。
- `Sparkles` 更适合表达“技能 / 能力增强 / 预设能力”。
- `Bot` 在当前助手产品语境下，最接近“AI 模型选择”的直觉认知。

## 5. 实施约束

实现时应采用最小变更路径：

1. 在聊天输入区 4 个入口上直接替换图标组件。
2. 优先复用现有 `lucide-react` 导入，不新增其他图标依赖。
3. 仅在确有必要时删除这 4 个入口对应的旧自定义图标分支。
4. 不得顺带改动其他导航、侧栏、工作台或设置页面图标。

## 6. 受影响文件

预期受影响文件如下：

- `src/renderer/App.tsx`
- 如仅为样式兼容所必需，可触达 `src/renderer/styles.css`

本次设计不要求修改测试文件；只要 `data-testid` 和交互行为不变，现有 smoke 应继续成立。

## 7. 验收标准

实现完成后，必须满足以下验收条件：

1. 聊天输入区底部 4 个入口均显示新的语义图标。
2. 图标映射与本设计文档完全一致，不允许临时替换为其他近似图标。
3. 上传文件、工具、技能、模型 4 个入口的 hover、active、badge、popover 表现与现状一致。
4. 现有 `data-testid` 保持不变，相关 smoke 不因图标替换失效。
5. 至少完成与该变更直接相关的类型检查和最小 UI 验证。

## 8. 风险与控制

主要风险不是功能逻辑，而是实现时顺手扩大修改范围。控制方式如下：

- 将变更限制在聊天输入区 4 个入口。
- 不因为引入 `lucide-react` 图标而统一替换其他自定义 SVG。
- 验证只围绕图标展示和现有交互是否保持稳定展开。

## 9. 结论

本次工作应作为一次局部、可验证的 UI 语义修正处理。实现目标不是“重做聊天输入栏”，而是在不改变现有行为的前提下，将 4 个关键入口替换为更易理解的现成图标。
